# Smart Health revision: Juno runbook

All new StudentLife numbers come from one retraining pass. Every table and
figure is then generated by one script from those records, so they cannot
disagree with each other (Reviewer 1, Q1/Q2).

## 1. Set up (once, about 15 minutes)

```bash
cd /work/dod220001
scp -r <laptop>:juno .               # this folder
bash juno/setup.sh                    # clones the repo into sl_rev/, installs packages
# copy the preprocessed pickle from the repo's GitHub Release into
#   sl_rev/data/training_data/shuffled_splits/
cd sl_rev
python3 juno/make_horizon_data.py     # writes data/horizon/horizon_{1,2,3}.pkl
```

First check what hardware Juno offers: `sinfo -o "%P %G %l"`. If there is
a GPU partition, uncomment the two `##SBATCH` lines in `train_array.sbatch`.
CPU-only also works. The model is small and the batch size is 1, so CPU is
slower but usable.

## 2. Smoke test (about 10 minutes)

```bash
sbatch --array=1 --time=00:30:00 --export=ALL,EPOCHS=2,TAG=smoke juno/train_array.sbatch
# when it finishes:
ls data/cross_val_scores/*smoke*        # one .pkl
python3 juno/analysis_revision.py --tag smoke --quick   # runs end to end; the numbers are meaningless at 2 epochs
```

## 3. Full run (80 array tasks; each task is one configuration × one repetition)

```bash
sbatch --array=1-80%20 juno/train_array.sbatch
```

| Tasks | Config | What it is | Answers |
|---|---|---|---|
| 1–10 | base | LSTM baseline, `all_in_one` | Tables 1–4 |
| 11–20 | p1 | CALM-Net, 1 branch, `one_for_each` | Tables 1–4 |
| 21–30 | p3 | CALM-Net, 3 branches, `one_for_each` | Tables 1–4 |
| 31–40 | base_asym05 | asymmetric loss, λ = 0.5 | R1-2, Table 5 |
| 41–50 | base_asym10 | asymmetric loss, λ = 1.0 | R1-2, Table 5 |
| 51–80 | base_h{1,2,3}, p3_h{1,2,3} | labels shifted 1–3 EMA responses ahead (5 reps each) | R2-3 |

Before running anything else, check that tasks 11–30 reproduce micro-F1 of
about 0.60/0.61 (`results/rev/T1_f1.csv`). If they don't, stop and
investigate first.

## 4. Analysis (about 20 minutes on one CPU node)

```bash
python3 juno/analysis_revision.py --tag rev       # writes results/rev/
tar czf results_rev.tgz results/rev               # bring this back to me
```

## 5. WESAD (decide first; see the note in the manuscript)

The reference pipeline evaluates with `shuffle=True` and saves no window
index, so the submitted WESAD trajectories were not in time order. To
regenerate them:

```bash
cd wesad
python3 ../juno/wesad_fix_and_dt.py patch       # shuffle=False, chronological order, saves fnames
python3 -m main personalize loocv               # needs the raw WESAD data + preprocessing, as before
python3 ../juno/wesad_fix_and_dt.py dt --records data/exp_res/personalize
```

If that can't be done before about 12 October, withdraw the WESAD ΔT
section instead. That is a defensible response to R2-4.
